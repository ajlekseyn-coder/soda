# Проект стандарта: согласованность представления данных в приложении

**Статус:** проект стандарта проектирования, нормативная версия 0.4; кандидат для
проверки на приложениях. В Soda реализован исследовательский анализ путей данных.
Он сообщает структурные кандидаты и пробелы доказательства отдельно от нарушений.
**Рабочее имя запаха:** `representation_churn` — жонглирование представлениями.
**Область:** связанный поток данных между методами, классами и компонентами
приложения, включая разные файлы. Объекты, примитивы и структуры данных.
**Поставка:** по решению пользователя `representation_churn` включён в
`RuleCatalog::standard()` и генерируемые конфигурации. Исследовательские находки
публикуются отдельно и не меняют результат quality gate. Существующие явные
конфигурации выполняют только перечисленные в них правила.
Инструкция и ограничения реализации: [структурные метрики](../STRUCTURAL_METRICS.md#representation_churn).
Независимая панель оценивала исходный снимок v0.4 до реализации; его точный текст
и SHA-256 сохранены в [архиве панели](../research/representation-consistency/panel-v04-fresh.json).

## 1. Основное требование

> Внутри связанного участка обработки одного понятия следует согласовать
> представление, когда это устраняет распределённую интерпретацию данных или
> снижает стоимость изменения. Смена представления должна
> иметь конкретное назначение и быть сосредоточена на границе, которой она нужна.
> Потребители не должны регулярно извлекать значения и восстанавливать объекты
> только для согласования соседних внутренних API.

Требование относится к работе приложения: результат одного компонента становится
аргументом другого, проходит обработку и передаётся дальше. Чистые, короткие
методы по отдельности могут скрывать несогласованность всего пути.

Рассматриваются, например, такие связанные цепочки:

```text
Repository::load(): Str
  → Normalizer::normalize(Str): string
  → Cleaner::clean(string): string
  → Formatter::format(string): Str

Repository::load(): Collection
  → Extractor::extract(Collection): array
  → Filter::apply(array): array
  → Calculator::calculate(array): array
  → ResultAssembler::assemble(array): Collection
```

Это не требование одного класса для всего приложения. Для разных понятий,
подсистем и внешних контрактов могут быть нужны разные представления. Проверяется
согласованность конкретного потока и назначение переходов между его участками.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Понятие | То, что данные обозначают в рассматриваемой операции: текст сообщения, сумма в определённой валюте, интервал дат, набор заказов. |
| Представление | Способ выразить понятие в программном контракте: класс, примитив, enum, структура массива, формат или сочетание значений. |
| Поток данных | Связанная передача результата через возвращаемые значения, аргументы, поля и создание объектов. Сходство имён методов не устанавливает связь. |
| Участок обработки | Часть потока, где компоненты продолжают работать с одним понятием при согласованных предположениях о его смысле и контракте. |
| Преобразование представления | Извлечение, упаковка, разбор или конверсия данных для другого программного контракта. |
| Граница представления | Место, где другой контракт нужен по конкретной причине: хранение, транспорт, внешний API, формат, единицы, самостоятельная подсистема, общий внутренний API, вычислительный участок или контракт стадии. |
| Жонглирование представлениями | Распределённая смена представлений в ходе внутренней обработки, из-за которой соседние компоненты постоянно согласуют типы и заново интерпретируют данные. |

Понятие может сохраняться, хотя значение меняется: очищенный текст остаётся
текстом сообщения, а сумма после скидки остаётся суммой в той же валюте.
Происхождение из одного значения ещё не доказывает сохранение понятия: длина
текста, налоговая ставка или число заказов обозначают другой результат.

Разные имена классов не доказывают смену смысла. Одинаковый PHP-тип также не
доказывает согласованность: `string` может обозначать исходный текст, JSON или
кодированное значение; `int` — сумму в разных единицах. Такие различия должны
следовать из контрактов, а не из догадки анализатора.

## 3. Требования к проектированию

### 3.1. Согласованные внутренние контракты

Компоненты одного участка обработки следует согласовать по основному
представлению понятия, если это снимает с потребителей повторяющиеся обязанности.
Самостоятельно полезные общие API могут сохранять свой контракт: совпадение
типов само по себе не оправдывает изменение их публичного API.
Низкоуровневая функция, принимающая примитив, может использоваться внутри
реализации без распространения примитива по остальным компонентам.

Основное представление выбирают по существующему контракту, операциям и
инвариантам. Им может быть класс, примитив или простая структура. Само наличие
обёртки в начале потока не делает её автоматически лучшим выбором для всех этапов.

Сохранение понятия не означает одинаковых допустимых состояний на всех стадиях.
Если полезный инвариант объекта не действует для промежуточного результата,
участок разделяют по контрактам стадий. Примитив внутри такого участка допустим
и при полезном исходном объекте.

### 3.2. Обоснованная смена представления

Для смены представления должна быть понятна причина: какой следующий контракт
требует другой формы, что преобразуется и какие гарантии действуют после этого.
Расположение в папке `Services`, имя `DTO` или наличие класса `Converter`
самостоятельно не обосновывают границу.

Достаточно ясного API и реализации; стандарт не требует отдельного документа,
атрибута, интерфейса или нового адаптера для каждого перехода. Дополнительное
описание полезно, когда назначение границы нельзя восстановить из кода.

### 3.3. Локализация преобразований

Компонент, которому требуется другое представление, должен по возможности
сосредоточить преобразование у своего входа или выхода. Внешний контракт не
должен заставлять несвязанных внутренних потребителей подготавливать его форму.

Место адаптации выбирают с учётом направления зависимостей. Общий транспортный
клиент может сохранять собственный API; преобразование выполняет существующий
вызывающий компонент или адаптер, которому доступны оба контракта. Локализация
не требует зависимости инфраструктуры от доменных типов или нового класса.

Например, клиент внешнего API может сам извлечь строку из `Str` непосредственно
перед вызовом API. Предшествующие обработчики текста сохраняют свой контракт.
Возвращаемые внешние данные преобразуются в принятое внутреннее представление
в месте, где устанавливаются его гарантии.

### 3.4. Сохранение гарантий

При преобразовании должны учитываться действующие гарантии: единицы, валюта,
валидность, структура элементов, ключи, порядок, точность, идентичность,
изменяемость и способ обработки ошибок.

Для вычисляемых значений учитываются ленивость, материализация, однократность и
повторяемость обхода, момент вычисления и ошибок, владение ресурсами, память и
затраты вычисления. Для объектов — также aliases, снимок состояния, версия и
право на изменение. Эти свойства могут обосновывать отдельное представление.

Восстановление того же класса в конце не доказывает сохранение этих гарантий.
Например, создание нового объекта может повторно валидировать данные или менять
идентичность. Такая работа должна сохраняться при исправлении потока.

### 3.5. Поведение рядом с контрактом

Повторяющиеся операции над представлением следует выразить там, где их контракт
понятен и устойчив: методом существующего объекта, связной функцией или операцией
существующего компонента. Concern может организовать операции владельца.

Добавление класса, wrapper или fluent-метода оправдывается полезной операцией,
инвариантом или границей. Прохождение проверки само по себе не оправдывает
расширение API. Обычные методы с согласованными типами также удовлетворяют
стандарту.

Concern явно описывает требования к владельцу и не вводит скрытые зависимости
на его поля. Fluent-вариант должен различать изменяемый builder и цепочку новых
значений: порядок эффектов, исходный объект и его aliases сохраняют обязательства.

## 4. Когда появляется запах

Сильный повод для ревью возникает, когда связанный поток содержит несколько
преобразований одного понятия, а промежуточная обработка распределена между
компонентами с разными представлениями. Обратное создание исходного типа делает
такой путь особенно заметным:

```text
Str → string → обработка в нескольких компонентах → Str
Money → число и валюта → расчёт в потребителях → Money
DomainObject → DTO → array → обработка → DTO → DomainObject
```

Признаки практической цены:

- Изменение представления требует согласованных правок нескольких внутренних API.
- Потребители повторяют извлечение полей, распаковку и создание объектов.
- Смысл и гарантии типа приходится восстанавливать из параллельных параметров.
- Основные операции исходного типа воспроизводятся в промежуточном представлении.
- Потребитель должен знать, какие предыдущие компоненты уже изменили форму данных.
- Один и тот же переход повторяется в независимых путях приложения.

Для вывода о нарушении нужно установить хотя бы одну конкретную цену из этих
признаков и отсутствие полезного назначения перехода. Сама цепочка — кандидат
на исследование. Перенос прежней распаковки в один класс или private-метод не
подтверждает улучшения: нужно показать, какая обязанность исчезла у потребителя.

Полезная граница не оправдывает весь окружающий поток: внутри каждого участка
до и после неё проверяют распределённую адаптацию отдельно. Например, наличие
HTTP-запроса в конце сценария не обосновывает промежуточные массивы всех сервисов.
Также не требуется ждать второй копии кода: один путь уже может распределять
знание о валюте, округлении или схеме между независимыми потребителями.

Обратный переход не обязателен для нарушения стандарта: неоправданное
`Object → DTO → array` также может рассеивать один контракт по приложению.
Однако без обратного перехода автоматическому детектору сложнее отличить этот
случай от полезной цепочки самостоятельных контрактов.

Количество разных типов, классов или преобразований само по себе не определяет
качество. Эти признаки используются для восстановления пути и оценки цены
изменения; назначение границ оценивается отдельно.

## 5. Пример между компонентами приложения

`Str` ниже — условный пользовательский объект текста, не конкретный API
фреймворка. Участники находятся в разных файлах; вызовы координатора показывают
связь их аргументов и результатов.

Это пример для ручного ревью, а не готовый fixture детектора: тело `Str` ниже
не задано. Для автоматического доказательства нужны его реализация или профиль.

### До

```php
// TextRepository.php
public function load(int $id): Str
{
    return new Str($this->storage->read($id));
}

// TextNormalizer.php
public function normalize(Str $text): string
{
    return trim($text->value());
}

// TextCleaner.php
public function clean(string $text): string
{
    return str_replace('obsolete', '', $text);
}

// TextFormatter.php
public function format(string $text): Str
{
    return new Str('Message: '.$text);
}

// MessageHandler.php
public function handle(int $id): Str
{
    $text = $this->repository->load($id);
    $normalized = $this->normalizer->normalize($text);
    $cleaned = $this->cleaner->clean($normalized);

    return $this->formatter->format($cleaned);
}
```

Каждый метод короткий. Но нормализация переводит публичный контракт обработки в
строку, очистка продолжает его, а форматирование восстанавливает объект. Если у
`Str` есть полезные операции или гарантии, промежуточные компоненты обходят их и
должны самостоятельно понимать допустимую строку.

### Вариант исправления: сохранить объектный контракт

Этот вариант выбирают, если операции уже принадлежат полезному контракту `Str`
или их добавление снимает доказанную обязанность потребителей. Совпадение типов
не является самостоятельным основанием добавить показанные методы.

```php
// TextNormalizer.php
public function normalize(Str $text): Str
{
    return $text->trimmed();
}

// TextCleaner.php
public function clean(Str $text): Str
{
    return $text->without('obsolete');
}

// TextFormatter.php
public function format(Str $text): Str
{
    return $text->prefixedWith('Message: ');
}
```

Координатор сохраняет ту же форму вызовов; участники согласованы по типу.
Предполагается, что показанные операции `Str` возвращают новый объект и сохраняют
поведение исходных функций. Если это не так, пример требует другого исправления.
Объект может внутри использовать строковые функции и private helpers.

Возможен и другой результат ревью: если `Str` только хранит строку и не даёт
полезного контракта, весь внутренний участок может согласованно работать со
`string`. Перед таким изменением нужно проверить валидацию, идентичность и
обязательства публичных потребителей. Создавать три новых метода обёртки только
ради исчезновения предупреждения не требуется.

### Вариант исправления: согласовать примитивный участок

Если обработчики являются общими строковыми операциями, репозиторий может
сохранять полезный `Str`, а существующий координатор локализовать адаптацию.
Контракты нормализатора, очистителя и форматирования остаются строковыми:

```php
// TextNormalizer.php
public function normalize(string $text): string
{
    return trim($text);
}

// TextCleaner.php
public function clean(string $text): string
{
    return str_replace('obsolete', '', $text);
}

// TextFormatter.php
public function format(string $text): string
{
    return 'Message: '.$text;
}

// MessageHandler.php
public function handle(int $id): Str
{
    $text = $this->repository->load($id);
    $normalized = $this->normalizer->normalize($text->value());
    $cleaned = $this->cleaner->clean($normalized);

    return new Str($this->formatter->format($cleaned));
}
```

Выигрыш здесь — нормализатор и форматтер больше не знают об упаковке `Str`; места
адаптации сосредоточены в координаторе. Если исходный контракт уже самостоятельно
полезен и цена адаптации отсутствует, допустимый итог ревью — оставить цепочку.
Пример не доказывает необходимость менять существующий публичный API.

Локализация упаковки достаточна, только если промежуточные API не воспроизводят
правила исходного понятия. Координатор, передающий валюту и округление четырём
сервисам, ещё не устранил распределённую интерпретацию финансового контракта.

### Вариант исправления: обычная операция существующего владельца

Если три обработчика являются одноразовыми деталями `MessageHandler`, без
самостоятельных потребителей и обязательств, обработку можно выразить его методом:

```php
// MessageHandler.php — тело существующего класса
private function prepareText(string $text): string
{
    $normalized = trim($text);
    $cleaned = str_replace('obsolete', '', $normalized);

    return 'Message: '.$cleaned;
}
```

`handle()` извлекает строку, вызывает `prepareText()` и устанавливает конечный
объектный контракт. Такой метод можно разместить в concern этого владельца,
если это помогает организовать его связное поведение. Само объединение сервисов
не доказывает исправления запаха: оно допустимо ради понятного сценария и
устранения ненужных зависимостей, с проверкой остальных потребителей.

Полезный `NonEmptyText` также может потребовать строковый участок: очистка
`'obsolete'` временно даёт `''`, а форматирование — `'Message: '`. Создание
`NonEmptyText` после каждого этапа изменит момент ошибки. Исходный и конечный
инвариант сохраняют на своих границах; три новых метода обёртки этого не решают.

### Скрытая цена: сумма и правила округления

```php
// Checkout.php
$minorUnits = $discounts->apply($price->minorUnits(), $discount);
$minorUnits = $fees->apply($minorUnits, $fee);
return new Money($minorUnits, $price->currency());
```

Методы короткие, числа типизированы. Если `Discounts` и `Fees` сами выбирают
округление, а контракт `Money` уже задаёт валюту, единицы и правила округления,
этот путь распределяет финансовый контракт. Ревью должно показать конкретные
формулы в обоих компонентах и какую правку потребует изменение этого правила.
Само имя `Money` и наличие числового расчёта такого вывода не доказывают.

Например, при обязательном общем правиле округления эти тела требуют двух правок:

```php
// Discounts::apply()
return (int) round($amount * (1 - $discount), 0, PHP_ROUND_HALF_UP);

// Fees::apply()
return (int) ceil($amount * (1 + $fee));
```

Если разные правила намеренно принадлежат разным операциям, это другой контракт:
два вызова математических функций сами по себе не являются нарушением.

Исправление может использовать существующие операции `Money` либо один
существующий компонент расчёта, принимающий и возвращающий `Money`. Concern
может организовать операции владельца. Новый класс для каждого арифметического
шага не требуется. Если независимое вычислительное ядро уже имеет полезный
контракт minor units и получает согласованные правила на входе, его сохраняют.

## 6. Допустимые преобразования

| Случай | Почему другой контракт может быть нужен |
| --- | --- |
| Хранение и восстановление | Формат записи отличается от рабочего представления; чтение устанавливает внутренние гарантии. |
| HTTP, очередь, экспорт | Получатель требует транспортный формат или версию схемы. |
| Внешняя библиотека | Её API требует примитив или определённую структуру; адаптация сосредоточена у вызова. |
| Общий внутренний API | Строковый обработчик или алгоритм массивов полезен независимым потребителям; адаптация локализована без дублирования доменных правил. |
| Вычислительный участок | Пакет, числовое ядро или материализация нужны алгоритму; гарантии установлены на входе/выходе. Если выигрыш производительности — единственное основание, его проверяют измерениями; требуемый контракт алгоритма сам обосновывает переход. |
| Снимок, проекция, владение | Контракт фиксирует состояние и версию, ограничивает операции и отделяет live entity от данных вычисления. Отдельная подсистема не обязательна. |
| Самостоятельная подсистема | У неё есть независимые обязательства, жизненный цикл или эволюция схемы. Даже отображение полей 1:1 может быть полезной границей. |
| Смена единиц или кодировки | Преобразование явно меняет контракт значения; правила потери точности и допустимых данных определены. |
| Внутренний алгоритм объекта | Публичный контракт сохраняется, а извлечение примитива и обратная сборка являются деталями реализации операции. |
| Новый результат | `Str → int` для длины или `Collection → Money` для суммы создают другое понятие. |
| Разные выходные ветви | Объект продолжается в основной обработке, а строка или массив отдельно отправляются в журнал или наружу. |

`Money → запись → Money` при сохранении и загрузке не равнозначно внешнему
разбору суммы для расчёта в нескольких внутренних сервисах. Одинаковая форма
пути не даёт одинакового решения.

Адаптация контейнера и преобразование его элементов должны рассматриваться
отдельно. Коллекция объектов и массив сериализованных данных могут обозначать
разные контракты. Детектор не должен объявлять их взаимозаменяемыми по названиям
`toArray`, `all` или `collect`.

## 7. Контракт будущей диагностики Soda

Стандарт проектирования шире первой автоматической проверки. Детектор должен
различать наблюдаемый путь, доказанную семантику преобразования и человеческую
оценку назначения границы.

Различаются три результата:

- **Факт:** подтверждённое соответствие конкретного входа, результата и перехода.
- **Кандидат:** связанный путь, требующий оценки смысла и назначения контрактов.
- **Нарушение стандарта:** ревью установило сохранение понятия, неоправданную
  распределённую адаптацию и её конкретную цену.

Первый прототип выдаёт отдельный исследовательский отчёт. Кандидаты не являются
нарушениями включённого правила, не влияют на exit code и не требуют изменения
кода ради нуля диагностик. Интеграция с quality gate — отдельное решение после
корпусной проверки. Отсутствие распознанной границы означает `unknown`.

### 7.1. Требуемые доказательства

Кандидат на диагностику должен содержать:

1. Связанный путь происхождения значения между реально разрешёнными вызовами.
2. Объявления участвующих входов и выходов, с файлами и строками.
3. Подтверждённые операции извлечения и создания представления, включая конкретные
   поля, аргументы и их соответствие.
4. Промежуточные этапы обработки, через которые это значение действительно проходит.
5. Сведения о распознанных границах и неизвестных участках пути.
6. Отдельные статусы зависимости от входа и сохранения понятия; источник каждого
   утверждения: наблюдаемое тело, подтверждённый профиль или неизвестность.

Описание представления включает известные типы контейнера и элементов, ключи,
shape, единицы, валюту, кодировку и версию схемы. Неизвестные параметры не
доказывают равенство. `Collection<Order>` и `Collection<Invoice>` нельзя считать
одним представлением по имени контейнера.

Одних сигнатур, названий `Service`, совпадения полей DTO или типов локальных
переменных недостаточно. Два значения одного класса могут быть независимыми.
Нельзя склеивать пути из взаимоисключающих ветвей в несуществующую цепочку.

### 7.2. Узкий первоначальный кандидат

Для первой версии разумен исследовательский кандидат на подтверждённый путь
`R1 → R2 → R1`: извлечение и восстановление представлены разрешёнными операциями,
между ними есть обработка и передача через контракты участников сценария.
Прозрачные forwarding-методы нормализуются. Оба перехода относятся к одному потоку,
а не к независимым примерам использования типов.

Два преобразования — форма исследуемого пути, а не бюджет допустимых конверсий.
Публичность и число владельцев деклараций не доказывают самостоятельности
компонентов и не оправдывают создание либо объединение классов ради метрики.

Даже полностью подтверждённый путь ещё требует оценки границ. Автоматическое
сообщение должно говорить о необходимости ревью согласованности, без утверждения
об отсутствии полезной архитектурной роли. Неизвестную семантику конструктора,
конвертера или вызова нельзя считать прозрачной конверсией.

Зависимость результата от входа не доказывает сохранения понятия: длина, хеш и
маска текста могут происходить из текста, но обозначать другой результат.
Неизвестный смысл отмечается отдельно; установленная смена понятия исключает
кандидат на согласованность этого понятия.

Если совместимость исходного и восстановленного представлений неизвестна,
подтверждённый round trip не объявляется: сохраняется только частичный путь с
причиной остановки. Для контейнеров это касается и элементов, и ключей, и
схемы. Если установленная смена единиц или кодировки нужна контракту, это
отдельная граница, а не нарушение из-за различия представлений.

Подтверждённая полезная граница разделяет участки ревью. Отображение транспортной
схемы позволяет проследить данные, но не отменяет транспортного назначения.
Исследовательский отчёт может сохранить путь как допустимый контрольный пример.

| Установленные факты | Исследовательский результат |
| --- | --- |
| Происхождение, совместимость и сохранение понятия подтверждены | Кандидат на ревью назначения границ и цены; нарушение ещё не доказано. |
| Происхождение и совместимость подтверждены, смысл неизвестен | Структурный research-путь с `concept_preservation=unknown`, без совета сохранять одно представление. |
| Установлена смена понятия | Исключён кандидат для исходного понятия. |
| Неизвестны происхождение, совместимость или эффекты, влияющие на путь | Частичный путь до разрыва с конкретной причиной; подтверждённый round trip не объявляется. |
| Установлена полезная граница | Раздельное ревью участков; сам переход допустим. |

Отдельный research-сигнал может показывать `R1 → R2 → R3`, но такой путь не должен
по умолчанию становиться нарушением только из-за трёх представлений.

### 7.3. Содержание сообщения

```text
TextRepository::load(): Str
  → TextNormalizer::normalize(Str): string
  → TextCleaner::clean(string): string
  → TextFormatter::format(string): Str

An extracted value crosses processing contracts and is rebuilt as Str.
Review the purpose and guarantees of each boundary. Compare keeping the current
contracts, a primitive processing region, and an object contract. Change only
when a concrete consumer obligation is removed and observable guarantees remain.
```

Этот совет допустим только при подтверждённом сохранении понятия. При неизвестном
смысле сообщение перечисляет факты и вопрос, без направляющего совета:

```text
Extraction and reconstruction are connected; the meaning of Processor::apply()
is unknown. This structural path does not establish that the same concept survives.
Inspect that operation before considering representation changes.
```

Реальная диагностика должна добавить места объявлений и преобразований, точки
вызова, длину подтверждённого пути и найденные ограничения анализа. Основная
позиция — ранний переход, рекомендации относятся ко всей цепочке. Несколько
входных путей к одной цепочке следует объединять, сохраняя участвующие места;
каждый forwarding-метод не должен создавать новое одинаковое предупреждение.

Автоматического исправления нет. Детектор не выбирает доменное имя, не создаёт
value object, не навязывает fluent API и не обещает сохранение поведения.
Пример вызова после исправления должен учитывать существующий публичный контракт.

## 8. Требования к межфайловому анализу

Нужен граф потока данных, а не только граф вызовов. Рёбра должны показывать
передачу конкретного результата в конкретный аргумент или поле. Вызов другого
метода без передачи рассматриваемых данных не продолжает этот поток.

Начальная область реализации может ограничиваться именованными локальными
методами/функциями, разрешёнными конструкторами, прямыми возвращаемыми значениями,
простыми присваиваниями и подтверждёнными преобразованиями. Примитивы участвуют
наравне с классами: `Str → string → Str` — обязательный положительный сценарий.

Ссылки, изменяемые aliases, виртуальные вызовы, динамические фабрики, замыкания,
отложенные вычисления и работа через поля требуют собственных доказательств.
Объявленный return type не доказывает происхождение результата. Отсутствие
информации о вызове должно прерывать доказанный путь либо оставлять явно
неопределённый research-результат.

Минимальный прототип требует отдельных фактов потока значений; существующий
граф классов или лексическое происхождение метода их не заменяет:

- Каждое локальное присваивание создаёт новую версию значения.
- Связь аргумента с возвратом сохраняется для конкретной точки вызова; summaries
  применяются отдельно, независимые вызовы одного метода не склеиваются.
- Для виртуального вызова нужен доказанный target: точный receiver, неизменяемый
  dispatch или явно заданная закрытая модель всех targets. Найденное тело базового
  класса и единственный известный implementer недостаточны.
- Запись через alias, escape или неизвестный эффект на отслеживаемое состояние
  инвалидирует зависимые доказательства. Первая версия исключает ссылки и
  изменяемые heap aliases; неразрешённый эффект даёт `unknown`.
- Первая версия может ограничиваться прямолинейными телами; ветви, циклы и
  неподдержанные вызовы явно обозначают разрыв, а не отсутствие запаха.

Библиотечные преобразования требуют проверенных семантических профилей или
явно заданных контрактов. Имя метода не заменяет профиль. Конструктор с валидацией
или эффектами не считается простым восстановлением контейнера.
Известную сборку с валидацией учитывают с её гарантиями и эффектами; неизвестную
не подменяют прозрачной упаковкой. Это разные состояния анализа.

Применимость профиля проверяют по точному callable, пакету/версии и предусловиям
вызова. Переопределённый метод или несовместимая версия не наследуют его доказательства
по имени; результат становится `unknown`. Evidence указывает профиль и проверку
его применимости. Профиль — явно доверенный контракт, а не эвристика.

HTTP, очередь и хранилище могут соединять участки работы приложения, но статический
анализ не должен автоматически связывать их по одинаковому типу или имени поля.
Без подтверждённого отображения транспортной схемы путь на этой границе заканчивается.

Граф должен хранить компактные факты и позиции, освобождая AST после файла.
Поиск путей должен быть ограниченным и устойчивым к циклам. Лимиты глубины,
числа путей и неполнота разрешения должны быть описаны: достигнутый лимит не
доказывает отсутствия других преобразований или пригодности границы.
Отчёт раскрывает охват, неразрешённые и усечённые пути и причины остановки.
Нужно измерять время, память и полезность находок отдельно от доли разрешённых
вызовов. Отсутствие находок не доказывает согласованность всего приложения.

### 8.1. Минимальный исследовательский контракт фактов

Это требования к будущему прототипу, а не существующая схема Soda. Сводка
callable должна содержать его идентификатор, позиции, входные слоты, версионированные
локальные значения, результат, отображения полей и неизвестные эффекты.
Ребро хранит источник и приёмник, точку вызова, операцию, происхождение доказательства
и отдельные статусы `data_dependency`, `concept_preservation`, `effects`.
Один флаг `known` не заменяет эти независимые свойства.

Summary задаёт предусловия, постусловия и затронутые слоты состояния; неизвестные
эффекты инвалидируют зависимые факты. Первая версия может исключить методы с
изменением receiver вместо предположения, что summary зависимости описывает
весь наблюдаемый эффект вызова. Template-параметры подставляются отдельно для
каждой точки вызова. Обязательные слоты представления сопоставляются совместно:
число из одного `Money` и валюта из другого не доказывают восстановление первого.
Неизвестная корреляция или template оставляют частичный путь.

| Операция | Минимальное условие переноса факта |
| --- | --- |
| Присваивание | Новая версия приёмника связана с конкретной версией источника. |
| Getter | Доступное тело читает установленное поле без неизвестной обработки; hooks и магия требуют отдельного профиля. |
| Конструктор | Подтверждено отображение аргумента в поле, включая promoted property; валидация и эффекты записываются отдельно. |
| Обработка | Профиль или доступное тело подтверждает зависимость результата; сохранение понятия оценивается независимо. |
| Вызов | Summary подставляется в аргументы конкретной точки вызова при доказанном dispatch. |
| Неизвестная мутация | Затронутые доказательства инвалидируются; отчёт показывает причину разрыва. |

Поиск ограничивает раскрытия вызовов, факты на callable, число свидетельств и
общий объём графа. Конкретные значения задают настройки прототипа и публикуют
в отчёте вместе с версиями профилей; оптимальные значения пока не установлены.
При достижении любого лимита обязателен `truncated` с названием лимита, а не
результат «путь отсутствует». Циклы не должны бесконечно расширять свидетельство.

## 9. Проверка исправления

Исправление оценивается по целому сценарию и его потребителям:

- Сократилось ли число мест, согласующих представление одного понятия?
- Какая обязанность исчезла у конкретного потребителя и не перенесена ли она
  механически в другой файл? Не выросла ли связность общих API?
- Остались ли ясные контракты входов, промежуточных операций и выходов?
- Сохранились ли значения, ключи, порядок, единицы, точность и формат?
- Сохранились ли валидация, ошибки, эффекты, идентичность и изменяемость там, где
  они имеют значение для вызывающего кода?
- Сохранились ли ленивость, число обходов, момент ошибок, ресурсы, память,
  snapshots, версии состояния и права на изменение?
- Не появились ли обязательные новые объекты и публичные методы без полезной роли?

Результат оценивается по сохранению гарантий и сокращению мест, согласующих
представления. Число методов и классов само по себе не подтверждает улучшения.

### 9.1. Решение ручного ревью

Ревью проходит от конкретного сценария к рекомендации:

1. Указать вход и наблюдаемый выход; перечислить реальную цепочку участников.
2. Назвать понятие, представления и действующие гарантии каждого участка.
3. Для каждого перехода установить самостоятельное назначение либо неизвестность.
4. Назвать конкретную цену: повторное знание, потерянная гарантия или связанная
   правка нескольких потребителей. Привести код, где она возникает.
5. Рассмотреть сохранение объекта, примитивный участок и сохранение текущей
   границы; выбрать вариант по обязанностям потребителей и поведению.

Итог фиксируют одним из трёх решений:

- **Исправить:** понятие сохранено, цена показана, переход не имеет полезного
  назначения; предложено исправление с проверкой потребителей и гарантий.
- **Оставить без изменения:** назначение границы установлено либо конкретная
  цена несогласованности отсутствует. Не нужно придумывать отдельную архитектурную
  роль для безвредного перехода. Это не оценка всего приложения.
- **Недостаточно данных:** неизвестны происхождение, смысл, назначение границы
  или обязательства потребителей. Неизвестность не является нарушением.

Необязательная запись ревью: **сценарий; цена и места; назначение границ или
неизвестность; решение; проверка поведения**. Для примера `Money`: Checkout;
два встроенных правила округления; общего правила требует контракт суммы;
сосредоточить правило в существующем владельце; сравнить значения и порядок
округления до/после на граничных суммах. Такая запись не требует нового файла
для каждого перехода и не утверждает, что пример уже прошёл исполняемую проверку.

## 10. Условия допуска автоматического правила

До появления поставляемой проверки нужны положительные и отрицательные сценарии:

| Группа | Что проверить |
| --- | --- |
| Распределённая обработка | `Str → string → Str` и `Collection → array → Collection` в разных компонентах и файлах. |
| Другие представления | Объект/примитив, объект/структура, объект/другой объект; без зависимости от конкретного имени класса. |
| Происхождение | Aliases, разные экземпляры одного типа, переиспользованные переменные, несовместимые ветви и независимые результаты. |
| Контекст вызова | Два независимых вызова одного helper не соединяются; запись и неизвестный эффект инвалидируют факты. |
| Корреляция и профили | Подмена currency/prototype, template в разных вызовах, несовместимая версия библиотеки и переопределение профилированного метода. |
| Допустимые границы | Транспорт, хранение, самостоятельные схемы, адаптеры и алгоритмы внутри владельца. |
| Смысл и гарантии | Смена понятия, единиц, структуры элементов, валидация и создание нового объекта вместо сохранения идентичности. |
| Стадии и ресурсы | Временно недопустимые для объекта состояния, курсор/генератор, bounded batch, snapshots и общий примитивный API. |
| Разрешение | Динамика, наследование, неизвестные библиотеки и конструкторы с эффектами должны давать корректную неопределённость. |
| Исправление | Сценарии до/после с проверкой поведения; более согласованный вызов без обязательного увеличения числа классов. |
| Эксплуатация | Ограниченный поиск, память, объединение диагностик, позиции и JSON evidence. |

Синтетические примеры подтверждают алгоритм, но не полезность рекомендации.
Нужен отдельный рассмотренный корпус приложений с находками и похожими допустимыми
путями. Точность и полнота пока не установлены. Отдельное решение пользователя
включило исследовательский анализ в стандартную поставку; допуск его находок
как нарушений quality gate по-прежнему требует проверки корпуса.

Корпус размечают исходами **исправить / оставить без изменения / недостаточно данных**.
Отдельно проверяют равнозначные сценарии с прямым вызовом, интерфейсом и callback,
чтобы обнаружить потерю охвата. Нужны исполняемые fixtures с прозрачной упаковкой,
известной валидацией и неизвестным конструктором; примеры §5 их не заменяют.
Для каждой рассмотренной находки записывают путь, назначение границ, цену,
решение, вариант исправления и способ проверки поведения. Отдельно измеряют
корректность восстановленных путей, полезность рекомендаций и неразрешённые
сценарии; объединять их в одну «точность» нельзя. Случаи с исходом «недостаточно
данных» сохраняют в отчёте и не записывают как корректные или ошибочные находки.

Публикуют числители и знаменатели: все сигналы, рассмотренные сигналы, подтверждённые
пути, каждое решение ревью, unknown/truncated и охват размеченного корпуса.
Полноту оценивают по независимо размеченным нарушениям в заявленной области,
а не только по выданным кандидатам. До допуска отдельно фиксируют состав корпуса,
независимую разметку, критерии ошибок, минимальную полезность, охват и ресурсные
пределы. Численные пороги определяет отдельное решение; наличие корпуса и успешная
синтетика сами по себе не являются достаточным основанием выпуска.
Результат ревью документа и матрица мнений: [независимое ревью](representation-consistency-review.md).

Связанные документы: [Practical design](../DESIGN_PHILOSOPHY.md) и
[Owner behavior rules](../OWNER_BEHAVIOR_RULES.md). `RepeatedForeignStateUpdate`
уже покрывает узкий арифметический шаблон над состоянием владельца; данный
стандарт рассматривает согласованность представлений в более широком потоке
приложения и не заменяет эту проверку.
